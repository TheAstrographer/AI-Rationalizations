Yes. The failures are almost always inherited human environment gaps, not model invention.

Common launch strings people cycle through for Uvicorn / uvicore until the environment finally matches:

python -m uvicorn main:app --reload
uvicorn main:app --reload
python -s -m uvicorn main:app
./uvicore http serve
(and variants with explicit host/port, workers, or full module paths)

These fail from unactivated venv, wrong Python on PATH, site-packages mismatch, missing package in the active environment, or a path that contains spaces and gets split. The agent simply retries the next string in the list because the root cause is external to the model.

The same pattern appears with React / Vite / Render hot-reload chains: stale or conflicting pip/npm state, outdated lockfiles, or path fragments produce repeated install/runtime errors. An unsupervised agent with skip-permissions then escalates the same broken chain (restarts → harder resets → broader cleanup commands). When a human-supplied path contains a space and gets tokenized, the resulting rm (or equivalent) can wipe far more than intended. That is execution of the inherited error, not the model inventing a target.

Quick-search autocomplete and lagging automated registries make it worse: they surface approximate or outdated metadata strings instead of locking the exact successful runtime command as the canonical entry. Agents then inherit the fragmented or stale data the same way they inherit path splits and launch mismatches.

This is why hard isolation (no skip-permissions, restricted users, sandboxed environments, mandatory human approval gates, backups) remains the only reliable brake for anything high-stakes. Banks, water systems, and similar infrastructure should not run unsupervised agents precisely because residual human setup gaps still exist and the model will execute the broken chain it is given. Updating the underlying stacks (Vite, Render, pip/npm tooling, etc.) reduces the frequency of the loops, but it does not remove the need for oversight.

The model is not “contriving” the failure or the data loss. It is over-correcting on the strings and environment state that were already incorrect.
